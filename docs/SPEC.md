> 版本 v0.1 · 2026-09-18
> 状态：**设计已锁定，待开工**
> 一句话定义：一个零依赖、零构建、纯静态托管的霓虹矢量精确平台跳跃游戏，跑在浏览器里，活在 GitHub Pages 上。

## 0. 已确认的决策清单

| 维度 | 决策 | 备注 |
| --- | --- | --- |
| 玩法类型 | 精确平台跳跃（Celeste 式） | 手感为王，非关卡数量取胜 |
| 核心动词 | 八向冲刺 + 墙跳 + 抓墙 | 无二段跳（冲刺即空中机动手段） |
| 技术栈 | 零构建 Canvas 2D + ES Modules | 无 npm 依赖、无打包器、无 CI 构建 |
| 关卡来源 | 手工设计 | 首版 12–15 关，字符网格 + 实体列表 |
| 视觉风格 | 霓虹矢量 | 深黑底 + 赛博青（安全）+ 品红（危险） |
| 音效 | WebAudio 程序化合成 | 零音频文件、零带宽 |
| 输入设备 | 键盘 + 触屏双支持 | 触屏 = 左虚拟方向区 + 右双按钮 |
| 失败机制 | 检查点 + 无限重试 | 死亡无惩罚，只有时间与死亡计数 |
| 叙事外壳 | 纯抽象 + 每关主题名 | 无故事线、无旁白 |
| 存档 | LocalStorage | 关卡进度 + 每关最佳用时 + 累计死亡数 |
| 部署 | GitHub Pages | 源码直接放 `main` 根目录（legacy pages） |

## 1. 技术架构

### 1.1 为什么是「零构建」

| 候选 | 结论 | 理由 |
| --- | --- | --- |
| **零构建 ES Modules** ✅ | 采用 | 源码即产物，`main` 根目录直推即上线，零 CI、零版本漂移、零构建失败风险。约束反而逼出更清晰的模块边界 |
| Phaser 3 + Vite | 否决 | 引擎约 1MB，且引入构建链 = 引入 CI 与缓存问题；本游戏用不到其物理与场景系统 |
| PixiJS | 否决 | 渲染优势要数百精灵同屏才体现，本作同屏实体 < 40 |

**硬约束**：`package.json` 只有 `{"type": "module"}` 与 script，**没有任何 dependencies / devDependencies**。

### 1.2 分层与依赖方向

依赖严格单向，禁止反向引用：

```
scenes  →  game  →  core
   ↓        ↓
 render   levels
```

- `core/` —— 引擎层，不含任何游戏语义（循环、输入、画布、音频、存储），可被任意项目复用。
- `game/` —— 规则层，纯逻辑，**不得触碰 DOM、不得触碰 Canvas**。物理与玩家状态机必须可在 Node 中裸跑（这是 `verify.mjs` 的前提）。
- `render/` —— 只读世界状态并绘制，**不得修改任何游戏状态**（摄像机震动除外，它是表现层状态）。
- `levels/` —— 纯数据，零逻辑。
- `scenes/` —— 场景编排，唯一允许同时接触输入、更新与渲染的层。

## 2. 手感规格（项目心脏）

### 2.1 单位系统

- 世界坐标使用**抽象世界单位**，与屏幕像素解耦。
- `TILE = 15` 世界单位，玩家碰撞盒 `10 × 12`（宽高各小于一格，保证狭窄通道可通过）。
- 视口高度固定 `18 格 = 270` 世界单位，宽度按视口宽高比自适应（16:9 时 = 32 格）。
- 渲染缩放 `scale = canvasCssHeight / 270`，为**浮点数**——霓虹矢量是矢量图形，浮点缩放反而更清晰，不做像素对齐。

### 2.3 三条「不公平感消除」原则

精确平台跳跃的乐趣来自**精确**，不是来自**苛刻**。以下三条是红线：

1. **输入永不丢失**：土狼时间 + 跳跃缓冲同时存在。玩家在落地前 0.12s 按下跳跃，落地瞬间必须起跳。
2. **死亡必可归因**：任何死亡都由玩家可观测的原因造成（碰到品红物体、坠落出界）。禁止「看不到的判定框」死亡——所有杀伤判定必须与视觉体积一致。
3. **检查点即安全区**：检查点激活后是绝对安全位置（周围至少一格无危险物），复活时给予 0.3s 无敌保护。

### 2.4 玩家状态机

7 个状态，转移条件全部在 `player.js` 中集中声明：

```
        ┌─────────────────────────────────────┐
        ↓                                     │
   [ IDLE ] ⇄ [ RUN ]                          │
        ↓                                        │
   [ JUMP ] → [ FALL ] ⇄ [ WALL_SLIDE ] → [ CLIMB ]
        ↓                     ↓                ↓
   [ DASH ] ←────────────────┴────────────────┘
        ↓
   [ DEAD ] → (检查点复活) → [ IDLE ]
```

- `DASH` 优先级最高，可从任意空中状态进入（有可用次数时）。
- `CLIMB` 需贴墙 + 按住抓键 + 耐力 > 0。
- 冲刺次数（1 次）的重置条件：**落地 / 墙跳 / 攀顶 / 踩弹跳板 / 穿过传送门 / 激活检查点**。

### 2.5 玩家能力标尺（实测，非估算）

由 `node scripts/abilities.mjs` 实测得出。**关卡的所有纵向/横向尺寸都必须落在这张表内。**
靠估算设计的障碍物，实测经常差 0.2 格就把玩家卡死 —— 而这种缺陷不会触发任何自检，
它既不违反物理，也不违反状态机。

| 机动手段 | 可达高度 | 关卡里的用途 |
| --- | --- | --- |
| 短按跳 | 0.39 格 | 微调、快速连跳 |
| 长按跳 | 1.59 格 | **常规台阶标尺** |
| 原地向上冲刺 | 5.45 格 | 中距离垂直机动 |
| 跳 → 顶点上冲 | **6.99 格** | **无墙环境的垂直天花板** |
| 贴墙纯攀爬（不墙跳） | **7.06 格** | 高墙的**朴素养法**（见下方说明） |
| 单面墙循环（爬 → 墙跳 → 上冲） | 无上限 | 长距离垂直通道 |
| 双面墙交替墙跳 | 无上限 | 竖井 |
| 原地水平冲刺（含滑行） | 5.50 格 | 冲刺可越的宽度 |
| 满速助跑跳（起跳→落地） | **4.31 格**（滞空 0.38s） | **跳跃可越的宽度** |

> ⚠️ **2026-09-18 修正**：上表的「满速助跑跳」原记录为 5.50 格，那是**探针量错了**——
> 它测的是「固定 0.5 秒内的位移」，而实际滞空只有 0.38~0.40 秒，
> 多出来的部分是**落地之后的跑动**。
> 按 5.5 格设计的 02/03/04 三关在实测中全部「差半格掉下去」。
> 教训：**能力标尺必须由探针产出，而且探针本身也要被审视** —— 推算不会发现自己量错了。
>
> 由此得出的安全设计值（留 ≥1 格余量）：
> 跳跃可越的坑 ≤ **3 格**；冲刺可越的坑 ≤ **4 格**；跳 + 空中冲刺可越的坑 ≤ **6 格**。

> ⚠️ **2026-09-18 第二次修正（由玩家试玩揪出，性质比第一次更严重）**
>
> 「贴墙纯攀爬」原为 **3.89 格**，而测试场的高墙是 **4 格** ——
> 玩家最直觉的解法（跳上去 → 抓住墙 → 往上爬）**差 0.11 格爬不上去**，
> 于是得出「这游戏根本过不去」的结论。
>
> 更值得警惕的是：上一轮我验证「墙跳重置耐力」时，测的是那套**反直觉的技巧循环**
> （爬到力竭 → 墙跳 → 上冲，能到 19 格）—— 它顺利通过了。
> **但玩家不会自己发现那套操作。** 他试的是最朴素的那种，而它刚好卡在门槛下。
>
> **教训：能力标尺要按「玩家的第一反应」来定，不是按「理论上存在的最优解」。**
> 技巧上限可以是 19 格，但**朴素解法的下限必须覆盖关卡里最高的那堵墙**。
> 一个只有高手能过的关卡，对普通玩家来说等同于 bug。
>
> 修正：`climbStamina` 1.10 → 2.60，`wallJumpVx` 215 → 175（降低飞离，让墙跳本身也更可用）。
> 现在朴素解法 **7.06 格**，覆盖所有设计中的单面墙高度。
> 同时补了**攀爬耐力的视觉反馈**：耐力 < 30% 时玩家闪烁变红 ——
> 坠落的原因必须看得见，这是「死亡必可归因」在视觉层的延伸。

**三条设计准则：**

1. **无墙环境的纵向障碍 ≤ 6.5 格。** 不要卡在 6.99 的极限值上 —— 那是实验室里的最优输入，
   真人玩家需要容错空间。
2. **超过 6.5 格的高度必须提供墙面或分段结构**（平台 / 传送门 / 弹跳板）。
   贴墙环境下没有硬上限，但需要「爬 → 墙跳 → 上冲」的操作循环，属于技巧型内容。
3. **水平坑洞 ≤ 5 格。** 5–6 格需要冲刺；超过 6 格必须给中途落脚点。

**为什么「墙跳重置空中机动」是必需的（一条被实测揪出来的设计缺陷）：**

修复前实测「贴墙纯攀爬」只有 **3.89 格，反而低于空手组合的 6.99 格** ——
**贴墙本该是优势位置，却成了劣势**，这违背玩家的直觉优先级。
根因是漏了 Celeste 的一条规则：墙跳必须重置冲刺次数与抓墙耐力。
修复后贴墙可达高度由「墙有多高」决定，不再有耐力硬上限。

对照数据：

| | 修复前 | 修复后 |
| --- | --- | --- |
| 贴墙（单面） | 3.89 格 | ≥19.2 格（无上限） |
| 贴墙（双面） | 19.2 格 | ≥19.2 格 |

另外实测发现：**「墙跳后靠空气加速折返」是条死路** —— 折返要 0.6 秒，
而墙跳只给 0.96 格，没飞回墙面就掉光了（32 次墙跳净升 0 格）。
**唯一有效的循环必须借助冲刺**（冲刺期间无重力，能把墙跳的动能兑现成净上升）。

## 3. 玩法系统

### 3.1 五类机关

| 机关 | 类型 | 行为 | 视觉语义 |
| --- | --- | --- | --- |
| **尖刺 / 激光** | 危险 | 静态方向尖刺；周期开关激光（含相位偏移） | 品红，脉冲呼吸 |
| **移动平台** | 载体 | 线性往返，玩家站上去获得平台速度（携带） | 青色描边 + 受光顶边 |
| **弹跳板** | 助力 | 踩上去大跳并**重置冲刺** | 青→品红渐变，踩下时闪白 |
| **崩塌地块** | 地形 | 踩上去 0.5s 后消失，2.5s 后恢复 | 裂纹逐渐显形，闪烁预警 |
| **传送门** | 位移 | 成对出现，出射端保留入射动量 | 双环旋转，品红内圈 |

危险物的**颜色必须唯一**：品红 = 会杀死你的东西。这条规则不允许被装饰性元素打破。

### 3.1.1 实现要点（三个容易错的地方）

**① 平台是单向的，绝不能写进 `world.isSolid`。**
写进去它就变成实心墙，玩家从下方跳不上去 —— 而移动平台最典型的使用场景恰恰是
「从下面跳上去」。实现上它通过一个额外的地面回调参与站立判定，
并在每帧做一次「穿过顶面则吸附」的修正。

**② 「是否站在平台上」必须用上一帧的位置判断。**
时序是：平台先移动 → 玩家后物理 → 最后才做交互修正。
等玩家物理结束时，它相对已经移动过的平台早就悬空了，用当前位置判断永远为假。
正确做法是记录双方的上一帧位置（`player.prevX/prevY` 与 `platform.px/py`）再做判定。

**③ 致命判定框必须 ≤ 视觉体积，而且不能简单内缩了事。**
尖刺是三角形，靠近尖端处视觉宽度趋近于 0，而矩形判定框不会 ——
所以「整格内缩一点」的做法会在尖端区域造成**不可归因的死亡**。
正确做法是取三角形的**最大内切矩形**（宽高各为格子的一半）。
自检里有一条断言专门看守这件事：判定框面积占比必须落在 `[15%, 30%]`，
下限防止缩到失效让尖刺形同虚设，上限防止超出视觉体积。

**④ 机关不能悬空。**
悬空的弹跳板玩家永远踩不到，等于关卡里的一个装饰品。
这类错误肉眼很难从截图上发现（画面看起来完全正常），
所以自检里直接断言「弹跳板下方是实心」「崩塌地块铺在坑洞之上」。

```js
  entities: [
    { type: 'moving-platform', from: { x: 6, y: 10 }, to: { x: 12, y: 10 }, period: 3.0 },
    { type: 'laser', from: { x: 20, y: 3 }, to: { x: 20, y: 12 }, period: 2.0, phase: 0.5 },
    { type: 'portal', id: 'a', at: { x: 5, y: 8 }, to: { x: 22, y: 8 } },
    { type: 'crumble', at: { x: 17, y: 11 }, w: 3 },
    { type: 'bounce', at: { x: 25, y: 14 } },
  ],

```

**网格图例**：`#` 实心墙 · `.` 空 · `^v<>` 四向尖刺 · `C` 检查点 · `E` 出口 · `B` 弹跳板 · `?` 崩塌地块

### 3.3 内容计划（12–15 关）

每关只教一件事，然后组合。章节按主题词命名（无故事线，仅作节奏标记）：

| 章节 | 关卡 | 主题词 | 教学目标 |
| --- | --- | --- | --- |
| I · 起步 | 01–03 | 初光 / 惯性 / 回响 | 移动、跳跃、可变跳高、土狼时间 |
| II · 冲刺 | 04–06 | 折射 / 突进 / 悬停 | 八向冲刺、空中机动、冲刺重置 |
| III · 墙面 | 07–10 | 攀附 / 之字 / 耐力 / 折返 | 抓墙、墙跳、耐力管理、连续墙跳 |
| IV · 机关 | 11–13 | 脉冲 / 崩解 / 门 | 激光节奏、崩塌地块、传送门守恒 |
| V · 综合 | 14–15 | 汇流 / 越界 | 全动词组合，无检查点终章 |

时长目标：单关 20–60 秒，全流程 8–15 分钟（含失败重试约 20–30 分钟）。

### 4.1 配色令牌（`palette.js` — 唯一颜色来源）

| 令牌 | 色值 | 用途 |
| --- | --- | --- |
| `void` | `#05060a` | 最底层背景 |

| `gridFar` | `#101828` | 远层视差网格 |
| `gridNear` | `#16213a` | 近层视差网格 |
| `player` | `#35e0ff` | **玩家**（青蓝，全站唯一「我」的颜色） |
| `playerGlow` | `#35e0ff` @ 22% | 玩家辉光 |

| `bounce` | `#5ff0d8` | 弹跳板（青系，属助力） |
| `danger` | `#ff2d7a` | **危险物**（品红，会杀死你的一切） |
| `dangerGlow` | `#ff2d7a` @ 30% | 危险物脉冲辉光 |
| `portal` | `#c16bff` | 传送门（紫，非危险，视觉上介于青与品红之间） |

**色相纪律**：全站只有三个色相参与语义——青（我 / 安全 / 助力）、品红（危险）、紫（位移）。其余一律用明度分级。

### 4.2 渲染管线（每帧顺序）

1. 清屏 `void`
2. 远层视差网格（跟随摄像机 × 0.25，极低对比）
3. 近层视差网格（跟随 × 0.55）
4. 地形：实心墙用暗面填充 + 顶部 1px 受光边（受光方向**恒为正上方**）
5. 机关：危险物用品红 + 呼吸脉冲，助力用青系
6. 粒子层（冲刺残影 → 拖尾 → 落地尘 → 死亡爆散）
7. 玩家：几何体（菱形 + 朝向指示）+ 辉光
8. 出口 / 检查点（暖白 / 已激活转青）
9. HUD（DOM 外壳，不进 Canvas）

### 4.3 伪辉光方案（关键性能决策）

`ctx.shadowBlur` 每帧成本极高，**禁止在循环体内使用**。替代方案：**多层描边法**。

```
同一形状描 3 遍：
  第 1 遍：lineWidth = 6px, globalAlpha = 0.10, 颜色 = 发光色   （外晕）
  第 2 遍：lineWidth = 3px, globalAlpha = 0.28, 颜色 = 发光色   （中晕）
  第 3 遍：lineWidth = 1.2px, globalAlpha = 1.0, 颜色 = 亮色     （核心）
```

成本仅 3 次 `stroke()`，视觉上足以产生霓虹感。仅玩家与出口允许额外叠加一层 `shadowBlur`（全屏范围内数量恒定，成本可控）。

### 4.4 性能预算

| 指标 | 上限 |
| --- | --- |
| 目标帧率 | 60fps @ 1920×1080 集成显卡 |
| 物理步长 | 固定 1/120s（每渲染帧 0–8 步，带步数上限防「死亡螺旋」） |
| 每帧 stroke/fill 调用 | < 600 |
| 同屏粒子 | ≤ 400（对象池固定容量，**禁止运行时分配**） |
| 每帧对象分配 | 0（除字符串外；热路径全部复用对象） |
| 首屏加载 | < 200KB（全部源码 + HTML，无外部资源） |

**对象池是硬性要求**：粒子、残影、碰撞结果全部预分配。GC 抖动是低端设备掉帧的头号杀手。

## 5. 音频规格（WebAudio 程序化合成）

**必须由用户手势解锁**：`AudioContext` 在标题页首次点击/触摸后 `resume()`。这条决定了标题页必须有一个「点击开始」而非自动进入。

| 事件 | 合成配方 | 时长 |
| --- | --- | --- |
| 跳跃 | 三角波 200→420Hz 上滑 + 快衰减 | 0.08s |
| 冲刺 | 白噪声爆发 + 锯齿波 600→180Hz 下滑 | 0.14s |
| 落地 | 正弦 80Hz + 短噪声脉冲 | 0.06s |
| 墙跳 | 方波 320→520Hz，略带回弹 | 0.09s |
| 弹跳板 | 正弦 220→880Hz 快速上滑 + 颤音 | 0.18s |
| 检查点 | 双音上行（660Hz → 990Hz） | 0.16s |
| 死亡 | 锯齿 400→80Hz 下滑 + 噪声 | 0.30s |
| 过关 | 三音琶音（523 / 659 / 784 Hz） | 0.45s |
| 传送 | 反向扫频（由远及近） | 0.12s |

**静音开关**必须存在并持久化到 LocalStorage。同帧同类音效**限频**（如同时踩到多个弹跳板，只响一次）。

## 6. 存档规格（LocalStorage）

单键 `neonleap.save.v1`，JSON 结构：

```json
{
  "version": 1,
  "unlocked": 5,
  "levels": {
    "01-first-light": { "cleared": true, "bestTimeMs": 18420, "deaths": 3 },
    "05-refraction": { "cleared": true, "bestTimeMs": 27330, "deaths": 11 }
  },
  "totals": { "deaths": 47, "playTimeMs": 1284000 },
  "settings": { "muted": false }
}
```

- **版本字段必需**：读档时版本不符则丢弃并重建（不尝试兼容旧结构，避免迁移代码腐烂）。
- **写入节流**：仅在「过关 / 解锁 / 切场景」时写入，禁止逐帧写。
- **写入容错**：`localStorage` 可能因隐私模式抛异常，全部写入包 `try/catch`，失败则降级为内存态（本次会话有效）。
- **重置入口**：标题页长按 2 秒可清档（隐藏入口，防误触）。

## 7. 输入规格

### 7.1 统一意图层

`input.js` 向游戏只暴露一个意图对象，键盘与触屏产出**完全相同**的结构：

```js
{
  moveX: -1 | 0 | 1,      // 水平方向
  moveY: -1 | 0 | 1,      // 垂直方向（攀爬 / 八向冲刺）
  jump: { held: bool, pressed: bool },
  dash: { held: bool, pressed: bool },
  grab: { held: bool, pressed: bool },
}
```

`pressed` 为**边沿触发**，每物理步后清除。游戏逻辑**永远不知道**输入来自键盘还是手指。

### 7.2 键位映射

| 动作 | 键位 |
| --- | --- |
| 移动 / 攀爬 | `方向键` 或 `WASD` |
| 跳跃 | `Z` / `空格` / `K` |
| 冲刺 | `X` / `J` / `Shift` |
| 抓墙 | `C` / `L` / `Ctrl` |
| 重开本关 | `R` |
| 暂停 / 返回 | `Esc` |
| 静音 | `M` |

### 7.3 触屏方案

- **左半屏**：虚拟方向区。触摸点即原点，滑动超过死区（12px）后按角度输出 8 向；**支持动态重定位**（手指滑出原区域后原点跟随）。不画固定摇杆底盘——只在触摸点绘制一个淡青圆环。
- **右半屏**：两颗按钮——跳跃（大，靠左下）、冲刺（小，靠右上）。抓墙 = 双侧同时按住（或长按跳跃按钮，二选一，Phase 6 实测决定）。
- **触屏按钮必须在 DOM 层**（`touch` 事件），不进 Canvas 渲染——避免污染渲染管线。
- 触屏 UI 仅在检测到 `pointer: coarse` 或首次触摸后显示，桌面端完全不出现。

## 8. 开发阶段与验收标准

每个阶段**必须通过验收才能进入下一阶段**，不允许「先欠着」。

### Phase 0 · 地基
**交付物**：`index.html`、`package.json`、`core/loop.js`、`core/view.js`、`core/input.js`、`scripts/serve.mjs`
**验收**：本地起服打开页面，看到深色画布 + 左上角帧率；键盘输入能改变意图对象并在画布上画出调试十字；`verify.mjs` 全绿。

### Phase 1 · 手感内核 ★ 最高优先级
**交付物**：`game/config.js`、`game/physics.js`、`game/player.js`、`render/palette.js`、`render/draw.js`
**验收**：在一个手搭的测试场里，能流畅完成「跑 → 跳 → 冲刺 → 墙跳 → 抓墙攀爬」全链路；土狼时间与跳跃缓冲可被**观测到**（调试模式显示时间窗倒计时）；**手感调参是纯数字游戏**——所有数值只在 `config.js` 里改。

> ⚠️ **这是整个项目最关键的一步。手感不对，后面 15 关全是白干。** 本阶段允许反复迭代，不设次数上限。

### Phase 2 · 机关系统
**交付物**：`game/entities.js`、`game/world.js`
**验收**：5 类机关全部可用；每类各有一个专用测试房间；平台携带速度、传送动量守恒、崩塌时序均通过 `verify.mjs` 断言。

### Phase 3 · 视觉成型
**交付物**：`render/backdrop.js`、`render/hud.js`、`game/particles.js`、`game/camera.js`
**验收**：伪辉光管线落地；摄像机前瞻 + 阻尼 + 死亡震动；粒子池 400 上限；**1080p 下 60fps 稳定**（用真实浏览器性能面板截图佐证）。

### Phase 4 · 关卡内容
**交付物**：`levels/01..15`、`levels/index.js`、`scenes/select.js`
**验收**：12–15 关全部可通关；每关有通关录像（replay）作为**可解性证明**，`verify.mjs` 重放全部录像并断言到达出口。

### Phase 5 · 声音与存档
**交付物**：`core/audio.js`、`core/storage.js`、`game/progress.js`、`scenes/title.js`
**验收**：9 类音效全部可听；音频需手势解锁；存档读写 + 版本丢弃 + 异常降级全部覆盖；静音开关持久化。

### Phase 6 · 触屏适配
**交付物**：`core/input.js` 触屏分支、DOM 触屏 UI
**验收**：真实手机（或 Chrome DevTools 触屏模拟）上能完整通关第一关；虚拟摇杆动态重定位可用；桌面端完全无触屏 UI 泄漏。

### Phase 7 · 验证与上线
**交付物**：`scripts/verify.mjs` 完整版、`scripts/e2e.mjs`、`README.md`
**验收**：`verify.mjs` 全部不变量通过；`e2e.mjs` 用真实 Chrome + CDP 模拟键盘跑通第一关并截图；线上 URL 实测可玩（**不能只看 workflow 变绿**）。

## 9. 验证策略

三层，缺一不可（沿用本项目工作区已验证的模式）：

### 第 1 层 · 纯逻辑自检（`verify.mjs`，Node 裸跑）

无需浏览器，覆盖所有可断言的不变量：

- 物理求解器：扫掠 AABB 不穿透（高速下落 1000 次随机用例）
- 玩家状态机：非法转移不存在（穷举 state × event 矩阵）
- 手感常量：数值区间合理性（如 `COYOTE_TIME` 必须 > `JUMP_BUFFER` / 2）
- 关卡数据：网格矩形、图例字符合法、spawn/exit 存在且唯一、检查点在实心块上
- 关卡可解性：**重放通关录像**，断言到达出口（物理必须完全确定性，无浮点随机）
- 配色令牌：`palette.js` 导出完整，危险色在关卡中无混用
- 逐文件 `node --check`（**必须逐文件**——`node --check src/main.js` 不跟随 import，曾因此漏掉整个页面起不来的语法错误）

### 第 2 层 · 真实浏览器 E2E（`e2e.mjs`，Chrome + CDP）

- 启动本地服务器 → 连接真实 Chrome → 模拟键盘输入序列 → 断言场景推进
- 截图留证（标题页 / 游戏中 / 过关页）
- 断言无控制台错误、无 404

### 第 3 层 · 人眼判断

截图与录屏交给用户看。**自动化永远不能替代「手感」与「好不好看」的判断。**

## 10. 部署方案

沿用本工作区已验证的约定（**不是** marketplace 里那套 `deploy_github_pages.sh`）：

1. 仓库 `X-LSH/neon-leap`，Pages 源 = `main /` (legacy)，**无工作流**。
2. 源码直接放仓库根目录 —— 零构建意味着不需要 Actions。
3. `index.html` 里所有路径用**相对路径**（`./src/main.js`），确保 `https://x-lsh.github.io/neon-leap/` 子路径下正常。
4. 两个必踩的坑：新仓库首跑需 `enablement: true`；https 推送前先 `gh auth setup-git`。
5. **上线后必须实测线上 URL**，不能只看推送成功。
6. Service Worker **不使用** —— 本作是短会话游戏，SW 缓存旧版本带来的麻烦远大于收益。

## 11. 风险与对策

| 风险 | 概率 | 对策 |
| --- | --- | --- |
| **手感调不到位**（最大风险） | 中 | Phase 1 单独立项、允许无限迭代；测试场先于关卡存在；参数与逻辑分离，改手感不动一行业务代码 |
| 关卡设计耗时超预期 | 高 | 字符网格 + 实体列表让改关卡变成改文本；每关先做「灰盒」验证可解性，再谈视觉 |
| 低端设备掉帧 | 中 | 对象池 + 多层描边替代 `shadowBlur` + 物理步长上限；Phase 3 用真实机器验证 |
| 触屏手感差 | 中 | 触屏方案在 Phase 6 实测，不佳则降级为「移动端只做简化的 3 键布局」 |
| 20+ 个 ES Modules 的请求开销 | 低 | HTTP/2 下无问题；若真实测到慢，再考虑合并，**不预先优化** |
| 浮点不确定性破坏 replay 验证 | 中 | 物理全部用固定步长 + 整数计数；禁用 `Math.random()`（用确定性 PRNG） |
